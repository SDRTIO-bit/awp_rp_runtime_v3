# 专属写作编辑 Agent 设计

日期：2026-07-26
状态：对话设计已确认，待书面规格评审
适用范围：Novel Mode 默认 Pi 交互 Agent

## 1. 背景

当前默认 Pi 交互 Agent 的定位是“受限调度 Agent”：理解 TUI 指令，然后调用项目状态、章节读取、规划、写作和审计工具。它适合自动化写作，却不适合作者主导的创作。

作者主导模式的核心问题不是缺少另一个自动规划模型，而是需要一个能长期对话、敢于质疑、可靠记录、帮助作者把想法想透的编辑。章节剧情必须来自作者与编辑共同确认的计划；不能在确认后再交给 Architect 二次生成，否则模型会用训练分布中常见的稳定套路覆盖作者的独特意图。

## 2. 目标

将默认 Pi 交互 Agent 改造成专属写作编辑 Agent：

1. 自动识别剧情、人物、世界观和章节设计意图，无需作者输入 `/skill` 或固定命令。
2. 像责任编辑一样反复追问、质疑、激发和确认，帮助作者充分表达脑中的想法。
3. 将所有作者消息确定性写入当前项目的本地日志，防止会话压缩、切换或异常导致遗忘。
4. 将随口想法保存为待整理素材，但未经确认不得改动正式设定或章节计划。
5. 将作者与编辑共同确认的结果保存为唯一权威的作者章节计划。
6. 作者明确批准后，由现有项目管线负责写作；对话 Agent 不直接生成章节正文。
7. 作品效果和目标读者优先于讨好作者。编辑必须提供具体、可辩论的判断，不进行空洞奉承。

## 3. 非目标

- 不让对话 Agent 直接代写完整章节。
- 不让 Architect 重写作者已经确认的章节剧情。
- 不把未确认的灵感自动提升为角色卡、世界观事实或章节计划。
- 不让 Reader Comfort Reviewer 直接修改正文或给 Writer 下达改写命令。
- 不在本阶段实现 P2 人工摩擦样本体系或 P3 Architect 校准。
- 不删除旧 `NovelBrain`；它继续作为显式 `NOVEL_AGENT_RUNTIME=legacy` 后备。

## 4. 创作权限原则

### 4.1 作者

作者对剧情走向、人物命运、核心设定、章节意图和最终取舍拥有决定权。作者可以推翻编辑建议，也可以明确修改既有设定。

### 4.2 专属写作编辑 Agent

编辑负责理解、追问、归纳、挑战和激发，不负责替作者决定答案。它可以提出候选方向、反例和风险，但必须标明这些内容尚未确认。

编辑忠于作品和目标读者，而不是作者当下的自我感觉：

- 不使用“很好”“很有潜力”等无证据赞美。
- 肯定时说明具体产生了什么叙事效果。
- 指出作者意图与读者实际获得的信息之间的差距。
- 对人物失真、因果薄弱、情绪自嗨、套路化和无变化场景直接提出异议。
- 被作者反驳后先说明判断依据和取舍，不立即无条件附和。
- 不为了顺滑而消灭有意的冲突、陌生感或不适。

### 4.3 Writer

Writer 负责将作者确认的剧情计划文学化。它可以发挥语言、动作、感官、潜台词和场景调度，但不能改变确定事件、角色边界、因果结论或明确禁止项。

### 4.4 Python 运行时

Python 是唯一的项目文件和状态写入者。它负责可靠落盘、版本管理、确认状态、权限校验、格式转换和管线调用，不进行剧情创作。

### 4.5 Architect

默认作者主导模式不调用 Architect。Architect 仅保留给旧的 AI 自主规划模式，不能位于“作者确认计划”和 Writer 之间。

## 5. 总体架构

```text
作者
  ↕
默认 Pi 专属写作编辑 Agent
  ├─ 自动调用 author-collaboration Skill
  ├─ 读取项目设定与历史素材
  ├─ 发散编辑：追问、质疑、激发
  └─ 收敛编辑：区分确定/候选/未决/禁止
  ↓
Python Authoring Service
  ├─ 原始创作日志
  ├─ 素材收件箱
  ├─ 作者章节计划及版本
  └─ 确认与权限校验
  ↓
AuthorPlanCompiler（确定性，无 LLM）
  ├─ 转换为现有 ChapterPlan 机械结构
  └─ 编译 Writer 章节契约
  ↓
Writer + 角色卡 + 世界观 + Ledger + 前文
  ↓
Quality → Mechanical Gate → Ledger Curator
```

Pi Agent 继续运行在现有隔离 Host 中。默认 shell、任意文件读写和网络工具保持禁用；新增能力只能通过 Python 暴露的项目绑定工具完成。

## 6. 本地持久化

### 6.1 原始创作日志

路径：

```text
<project>/.awp/authoring/journal/YYYY-MM-DD.jsonl
```

TUI 在向 Pi 发送作者消息之前，先由 Python 确定性追加记录。记录至少包括时间、会话 ID、当前项目、原始文本和消息 ID。

原始日志只用于防遗忘和追溯，不代表正式设定。即使 Pi 没有识别出创作意图，作者原话也不会丢失。

### 6.2 素材收件箱

路径：

```text
<project>/.awp/authoring/inbox.jsonl
```

Pi 识别到创作素材后，自动调用受限工具保存归纳条目。条目保留原始消息引用，并使用以下状态：

- `pending`：已保存，尚未纳入正式计划。
- `incorporated`：已被某个作者计划采用。
- `discarded`：作者明确放弃。

归纳条目不能覆盖原始日志，也不能自动修改正式设定。

### 6.3 作者章节计划

路径：

```text
<project>/.awp/authoring/chapter-plans/chapter_003.v1.json
```

每次实质修订生成新版本，不原地覆盖旧版本。计划状态为：

- `draft`：编辑整理中。
- `pending_confirmation`：已向作者展示，等待确认。
- `approved`：作者明确批准，可交给管线。
- `superseded`：已有更高版本替代。

批准记录包含作者确认消息 ID、时间、计划版本和内容哈希。

## 7. 作者章节计划合约

新增 `AuthorChapterPlan`。它面向创作意图，不以常见网文套路字段作为必填模板。核心内容包括：

- 项目、章节、版本和状态。
- 本章存在的原因。
- 目标读者及希望产生的阅读体验。
- 确定事件、顺序和因果关系。
- 场景开始状态、关键变化和结束状态。
- 人物当下目标、动机、选择、潜台词和性格边界。
- 世界观及连续性约束。
- 人物与读者各自掌握的信息。
- 必须保留的内容。
- 明确禁止擅自添加或改变的内容。
- 有意保留的歧义、空白或不适。
- Writer 可以自由发挥的表达空间。
- 尚未解决的问题。
- 来源素材 ID 和作者批准记录。

字段允许按作品需要留空；如果缺失内容会导致 Writer 必须替作者作关键决定，计划不能批准，应回到编辑对话继续澄清。

## 8. 编辑对话流程

### 8.1 自动进入

系统提示词要求 Pi 在发现剧情、人物、世界观、关系、场景或章节意图时自动使用 `author-collaboration` Skill。Skill 保持模型可调用状态，不要求作者记忆技能名称。

### 8.2 发散编辑

编辑根据当前项目设定和作者原话，优先追问真正影响作品的问题：

- 人物为什么在此刻做出这个选择？
- 这场戏结束后，事实、关系或自我认识改变了什么？
- 角色付出的代价和放弃的替代方案是什么？
- 读者在此处已经知道什么，还缺少什么支撑？
- 哪部分是作者有意的不适，哪部分只是尚未想清？
- 当前安排是否落入与人物无关的通用套路？

编辑可提供少量候选方向来激发作者，但候选项默认属于未确认素材。

### 8.3 收敛编辑

编辑持续维护四类信息：

- 已确定。
- 候选。
- 未决定。
- 明确禁止。

当信息接近充分时，编辑复述对作者意图的理解，让作者纠正误读；之后形成 `pending_confirmation` 计划摘要。默认采用深度编辑强度：即使已经具备可写条件，也继续检查一到两轮人物动机、情感落点和场景独特性。

只有作者明确表达“够了”“收敛”“按这个写”“开始写”等同意语义后，编辑才停止追问并请求批准计划。

### 8.4 批准与执行

计划的提出和批准必须发生在两个不同的作者轮次中。Pi 不能在同一轮内创建计划、替作者批准并启动管线。

批准后，编辑主动询问是否现在交给管线。只有再次获得明确执行同意，才调用写作入口。批准计划可以暂存，作者可在以后启动写作。

单章计划和多章安排都受支持。多章安排先保存为总安排，再拆分成独立、逐章可确认的 `AuthorChapterPlan`；Writer 每次只执行一章。

## 9. 确定性交接

新增 `AuthorPlanCompiler`，不调用任何 LLM：

1. 验证计划状态为 `approved`。
2. 验证没有阻塞性的未决问题。
3. 检查与角色卡、世界观、Ledger 和已写正文的显式冲突。
4. 为现有引擎补齐章节 ID、索引和机械预算。
5. 将作者确定的场景顺序映射为 `ChapterPlan.scene_beats`，不增删剧情节点。
6. 将作者计划的原意编译到 Writer 的 `chapter_contract`。
7. 保存作者计划版本、哈希与生成的 `ChapterPlan` 之间的来源映射。

冲突不能由编译器或 Writer 静默解决。若作者有意修改既有事实，应先通过编辑对话明确该修改并单独确认。

## 10. Writer 输入与优先级

Writer 接收：

- 作者批准计划及章节契约。
- 正式角色设定和当前角色状态。
- 世界观规则与连续性 Ledger。
- 已完成正文摘要和上一章结尾。
- 项目级文风要求。

Writer 不接收：

- 未确认的原始聊天。
- `pending` 素材。
- 编辑内部推理。
- Reader Comfort Reviewer 的改写建议。
- Architect 二次生成的剧情计划。

优先级为：

```text
作者确认的创作意图
  + 已确认的角色/世界观事实
  + 前文连续性
  > Writer 的表达偏好和通用习惯
```

当前 Writer 中“结尾必须有钩子”“必须有对话”“固定对白比例”等通用规则不能高于作者计划。作者主导模式只保留输出格式和机械安全约束；具体节奏、结尾形态和对白比例由作品需要决定。

## 11. 工具边界

交互 Agent 保留现有只读和执行工具，并增加项目绑定的作者协作工具。工具按职责分为：

- 读取：项目状态、章节、正式设定、素材、当前计划。
- 记录：归档素材、保存计划草稿和新版本。
- 确认：提交待确认摘要、批准指定版本。
- 执行：从已批准作者计划生成确定性写作输入并启动 Writer 管线。
- 审计：只读检查已生成章节。

所有写工具：

- 只允许访问当前项目根目录下的固定 `.awp/authoring` 路径。
- 拒绝任意路径参数和目录穿越。
- 使用 Python 原子写入或追加写入。
- 失败时返回明确错误，Pi 不得声称已经保存。

现有 `plan_chapter` 在默认作者主导模式中不再调用 Architect，应由“批准作者计划”的确定性交接入口替代。旧自主模式继续保留原行为。

## 12. 错误处理

- 原始日志写入失败：不向 Pi 发送消息，TUI 明确提示作者内容尚未安全保存。
- 素材归纳失败：原始日志仍在；提示归纳失败，不伪造成功状态。
- 计划与正式事实冲突：阻止批准或执行，返回具体冲突来源。
- 批准版本不是最新版本：拒绝执行，防止写旧计划。
- Writer 或后续管线失败：保留批准计划和来源映射，报告失败阶段，不自动改变剧情重试。
- Pi Host 故障：不静默回退 `legacy`；继续遵守现有显式运行时切换规则。

## 13. 与 Reader Comfort Reviewer 的关系

专属写作编辑 Agent 工作在写作前，帮助作者把意图和读者效果想清楚。Reader Comfort Reviewer 工作在成文后，只读识别可能的阅读摩擦。

Reviewer 可以把问题交回作者与编辑讨论，但不能直接修改正文，也不能把结论直接喂给 Writer。两者共同遵守项目章程：减少意外的理解阻塞，不消灭所有不适；最终创作答案由作者决定。

## 14. 测试策略

### 14.1 Node Host

- 默认系统提示词为专属写作编辑身份。
- `author-collaboration` Skill 可由模型自动调用。
- Pi 仍无 shell、任意文件写入和网络权限。
- 仅暴露批准的项目工具。

### 14.2 Python 持久化

- 每条作者消息在发送给 Pi 前先写入原始日志。
- JSONL 并发追加和异常恢复不破坏已有内容。
- 计划版本只增不覆盖。
- 路径穿越和跨项目访问被拒绝。

### 14.3 权限与确认

- 未确认素材不能进入正式计划。
- `draft` 和 `pending_confirmation` 计划不能执行。
- 同一轮不能提出、批准并执行。
- 旧版本批准不能覆盖新版本。
- 无明确作者执行同意时不能启动 Writer。

### 14.4 管线集成

- 作者主导模式不调用 Architect。
- 编译相同作者计划得到确定一致的 `ChapterPlan` 和章节契约。
- 场景节点不被编译器增删或改写。
- Writer 收到作者计划、角色、世界观和连续性上下文。
- 未确认聊天和 Reviewer 输出不进入 Writer。
- `legacy` NovelBrain 和自主规划模式继续可用。

## 15. 成功标准

1. 作者可直接用自然语言讨论创作，无需学习技能调用命令。
2. 每条作者消息都能在当前项目本地找到原始记录。
3. AI 能主动进行多轮编辑式追问，而不是快速生成套路大纲。
4. 所有进入正文管线的剧情内容都可追溯到作者批准的计划版本。
5. 默认作者主导路径中 Architect 调用次数为零。
6. Writer 不得接触未确认素材，且不能越过作者计划重新设计剧情。
7. 保存、确认或管线失败均不会被错误报告为成功。
8. 实际使用中发现的问题通过计划版本、日志和来源映射可复盘，并允许后续迭代。

## 16. 实施边界

首期只完成默认 Pi 写作编辑 Agent、自动共创 Skill、本地作者素材与计划持久化、确定性计划编译及 Writer 交接。界面以现有 TUI 对话为主，不新增复杂图形化编辑器。

设计允许后续根据真实使用反馈调整追问强度、计划字段和编辑提示词，但不得破坏以下冻结边界：

- 原始作者消息先落盘。
- 未确认内容不进入正式创作状态。
- 作者确认计划是唯一剧情依据。
- AuthorPlanCompiler 不调用 LLM。
- 默认作者主导模式不经过 Architect。
- 对话 Agent 不直接写整章正文。
